# 決定台帳

- 種別: 決定台帳 (追記専用)
- 対象: AI エージェントの作業を issue 単位で管理する Web アプリ

## 全体の方針 (2026-11-23)

- [決定] herdr と agent-loop に完全に代わるソフトウェアとして作る — 10 個以上のエージェントを同時に動かすと、どのプロジェクトのどのタスクが、どこまで進んだか分からなくなるため
- [決定] 階層は プロジェクト > issue > 状況 > AI とのやりとり とし、issue を管理の単位にする — ユーザーの判断
- [決定] Mac Studio に常駐する Web アプリにし、Tailscale 経由で複数の端末から使う — Mac Studio をサーバーとして使っているため
- [決定] 画面は herdr-app と同じようなものを想定する。中心の単位は端末から issue に変える — ユーザーの判断
- [決定] 初期版は Claude Code だけに対応し、Codex には対応しない — ユーザーの判断
- [決定] PC ではアプリのすべての操作を Vim キーバインドでできるようにする — ユーザーの判断
- [決定] PC の入力欄の中でも Vim の編集操作を使えるようにする — ユーザーの判断
- [決定] スマホには専用の UI を用意する — ユーザーの判断
- [保留] 細かい UI — これから詰める

## AI とのやりとり (2026-11-23)

- [決定] チャット表示にする — スマホ専用の UI と、Vim での発言単位の移動に合うため
- [棄却] Claude Code の端末画面をそのまま映す — スマホで読みにくく、アプリと Claude Code がキーを取り合うため
- [棄却] チャット表示と端末表示の両方を持つ — 同じセッションを 2 つのプロセスで同時に開くと発言が欠けることがあり、作る量も増えるため
- [保留] 実行方式は Claude Agent SDK (TypeScript) を第一候補とする — skills とプラグインの動作、質問への回答、再起動後の再開を試作で確かめてから決める
- [決定] 発言の一部を選択して引用できるようにし、複数の箇所に対してまとめて質問や指示を書けるようにする — AI の説明が分からず、複数の文に質問や指示をすることが多いため
- [決定] 選択した箇所からサイドチャットを始められるようにする。サイドチャットは元の会話とは別の独自のコンテキストを持つ — ユーザーの判断
- [決定] サイドチャットを終えるとき、確定した事項があれば元の会話へフィードバックし、なければ閉じるだけにする — ユーザーの判断
- [保留] サイドチャットの開始時に元の会話の内容を引き継ぐか — ユーザーの回答待ち → 解決 (下の「引用・質問・指示とレビュー」)

## タスクの管理 (2026-11-23)

- [決定] アプリ自体にタスクを管理する機能を実装し、GitHub に依存しない形にする — ユーザーの判断 → 撤回 (下の「引用・質問・指示とレビュー」)
- [棄却] GitHub の issue を正本にする — GitHub に依存しない形にするため → 撤回 (下の「引用・質問・指示とレビュー」)
- [保留] GitHub に依存しない範囲に、PR・CI・merge を含めるか — ユーザーの回答待ち → 解決 (下の「引用・質問・指示とレビュー」)
- [保留] 既存の GitHub の issue の扱い — ユーザーの回答待ち → 解決 (GitHub を正本に戻したので、取り込みは要らない) → GitHub を正本に戻す決定が撤回されたので、再び保留 (下の「タスクの管理をアプリに戻す」)

## 引用・質問・指示とレビュー (2026-11-23)

- [決定] タスクの管理は GitHub のままにし、issue と PR をアプリの中でもレビューできるようにする — ユーザーの判断 → issue の管理は撤回、PR のレビューは維持 (下の「タスクの管理をアプリに戻す」)
- [決定] PR・CI・merge は、GitHub を使うプロジェクトでは引き続き GitHub を使う — ユーザーの判断
- [決定] サイドチャットは元の会話を複製して始める — 経緯を踏まえて答えられるようにするため
- [決定] サイドチャットのツールは制限しない。作業させるかどうかは人が制御する — 質問に答えるために調査することがあるため
- [棄却] サイドチャットを読み取りと検索だけに制限する — 調査の妨げになるため
- [決定] 質問は、対象を Visual モードで選び、テキストを入力してサイドチャットを始める。形はチャットのスレッドと同じにする — ユーザーの判断 → 始める時点は、まとめて送信したときにする (下の「質問のストックと設計レビュー」)
- [決定] 指示は、対象を Visual モードで選び、プロンプトを入力してストックする。ストックはいつでも一覧で確認でき、指摘がすべて終わったらまとめて AI に送る。形は GitHub の PR のコメントと同じにする — ユーザーの判断
- [決定] 引用は 1 か所でも、複数の箇所をまとめた 1 件でもよい — 複数の箇所に対して 1 つの指示や質問をすることがあるため
- [決定] 引用・質問・指示は、AI の回答だけでなく、AI が作ったコードやドキュメントなどの成果物にも同じ操作でできるようにする — ユーザーの判断
- [決定] 引用・質問・指示の操作はすべてキーボードで完結させる — ユーザーの判断
- [決定] AI の回答とプロンプトの入力は、Vim でいう別々のウィンドウにする。主は回答の画面で、Normal モードで仮想スクロールし、`i` でプロンプトを入力する — ユーザーの判断
- [保留] 質問を、書いた時点ですぐ送るか、ストックして自分のタイミングで送るか — ユーザーの回答待ち → 解決 (下の「質問のストックと設計レビュー」)
- [保留] issue が無い段階の会話 (設計の開始、調査) の置き場所 — ユーザーの回答待ち → 解決 (下の「質問のストックと設計レビュー」)
- [保留] PR の差分に付けた指摘の送り先 — ユーザーの回答待ち → 解決 (下の「質問のストックと設計レビュー」)
- [保留] 回答・コード・ドキュメント・差分を CodeMirror の読み取り専用の画面で統一できるか — 試作で確かめる

## タスクの管理をアプリに戻す (2026-11-23)

- [決定] issue の管理はアプリで行う — issue を作るとエージェントが起動し、精査と設計、人の設計レビュー、実装、merge まで進める流れを組むので、アプリ側で管理できたほうが都合がよいため
- [棄却] issue の管理を GitHub のままにする — 上の流れをアプリ側で動かすのに都合が悪いため
- [決定] issue を作ったらエージェントが自動で起動し、内容を精査して設計する。人が設計をレビューして承認したら、実装と merge まで AI が進める — ユーザーの判断
- [決定] PR・CI・merge は、GitHub を使うプロジェクトでは引き続き GitHub を使い、PR はアプリの中でもレビューできるようにする — 先の決定のうち、issue の管理以外は変わっていないため
- [保留] 設計レビューの対象の形 (GitHub の設計 PR か、アプリ内の差分か) — ユーザーの回答待ち → 解決 (下の「質問のストックと設計レビュー」)
- [保留] 既存の GitHub の issue の取り込み — 移行の設計で決める
- [保留] 同時に動かすエージェントの上限 — フローの設計で決める

## 質問のストックと設計レビュー (2026-11-23)

- [決定] 質問も指示と同じくストックし、質問し終わったらまとめて送信する。送信した時点で、質問ごとにスレッド (サイドチャット) を始める — 質問も複数になることがあるため
- [決定] ストックした質問は取り消せるようにする — ユーザーの判断
- [棄却] 質問を書いた時点でスレッドを始める — 質問が複数のときにまとめて送れないため
- [決定] プロジェクトの直下に issue にしない会話を置けるようにし、そこから issue を作れるようにする — issue を作るとエージェントが起動するので、調査や相談を issue にすると不要な設計が始まるため
- [棄却] 会話を必ず issue に置き、自動で起動しない種別を用意する — 調査や相談にも issue が要るため
- [決定] PR の差分に付けた指摘は担当の AI へ送り、必要なものだけを選んで GitHub にも投稿できるようにする — ユーザーの判断
- [棄却] PR の差分の指摘をすべて GitHub のレビューコメントとして投稿する — 会話と GitHub を行き来することになるため
- [決定] 設計レビューは、アプリの中で設計書の差分と修正方針を見て承認する。承認するとアプリが設計書を既定ブランチへ反映し、実装へ進む。設計 PR は作らない — ユーザーの判断
- [棄却] 設計 PR を作り、アプリの承認で merge する — PR と CI を待つことになるため
- [保留] 既定ブランチへ直接 push できないプロジェクトでの設計書の反映 — フローの設計で決める → 解決 (UC-009 の代替フロー C と BR-047)
- [保留] issue の「下書き」の状態 — 書きかけの issue で起動しないための提案。フローの設計で決める → 解決 (issue の状態に「下書き」がある)
- [保留] 質問と指示を別々に送れるようにするか — 質問の答えを見てから指示を決める場合があるための提案。UI の設計で決める → 解決 (下の「設計の進め方」)

## 設計の進め方 (2026-11-23)

- [決定] 設計は `/dev-spec` (webapp モード) で進め、この台帳を入力にする — ユーザーの判断
- [決定] `/dev-spec` はフルコースで進める — 新規プロダクトで、画面と操作を詰める工程が要るため
- [決定] ストックした質問と指示は、質問だけ・指示だけ・全部の 3 通りで送れるようにする — 質問の答えを読んでから指示を直せるようにするため

## ユーザーストーリー (2026-11-23)

- [決定] 普通の端末 (シェル) は初期版では作らない — WezTerm などを使うため → 撤回 (下の「UI スケッチ」)
- [決定] Neovim からエージェントへ送る機能は初期版では作らない — ユーザーの判断
- [決定] issue の親子関係と依存、issue の優先度、キーのヘルプと変更を Must にする。ヘルプは `:h` で出せるようにする — ユーザーの判断
- [決定] 「自分待ち」だけで管理し、「長時間停止」を別に分けない — ユーザーの判断
- [決定] 既定では検証を通った変更を自動で merge し、指定した issue だけ merge の前で人の確認を待つ — ユーザーの判断
- [決定] 壁打ちから `/dev-spec` で設計を固め、`/dev-impl` で実装させる今の流れを変えない — ユーザーの判断
- [決定] agent-loop のように issue を拾い、状態に応じてエージェントに処理させる動きを変えない — ユーザーの判断
- [決定] 作業を失わないアプリの更新、プロジェクトごとの設定、画像の添付、会話とスレッドの一覧管理、閉じた issue の再開を Must にする — ユーザーの判断
- [棄却] agent-loop で進行中の issue を途中から引き継ぐ — 移行前に動いているものを終わらせれば足りるため
- [棄却] GitHub の障害専用の対応 — 止まった理由の表示と再開で扱えるため
- [決定] 「自分待ち」に、動きが無い時間の条件を入れない。一覧には最後の更新からの経過時間を表示する — 許可の確認や質問は Agent SDK のイベントで検知できるため
- [決定] issue が作られたら精査し、ready なら `/dev-impl` で実装を始める。その状況 (エージェントの実行の出力など) をアプリで確認できるようにする — ユーザーの判断
- [保留] 設計済みの issue を ready にする条件 (`/dev-spec` で人が認めた issue に限るか) — ユースケースで決める

## UI スケッチ (2026-11-23)

- [決定] PC は、左にプロジェクトと issue のツリー、中央に主のウィンドウ、右に必要なときだけスレッドやストックを開く。下に Vim 風のステータス行を置き、ヘッダーは置かない — 本文を広く使うため
- [決定] プロンプトは `i` を押したときだけ表示する — AI の回答を主に見せるため
- [決定] プロジェクトの issue は、状況ごとに区切った縦の一覧にする — `j` / `k` だけで全件をたどれるため
- [決定] ログイン画面は作らず、Tailscale の本人情報で判定し、本人以外には拒否の画面を出す — ユーザーの判断
- [決定] エラーは主のウィンドウ内に表示して「ホームへ戻る」「再読み込み」を置き、トーストは右上で成功・情報は 4 秒で消えエラーは手動で閉じて同時に 3 件までとし、ErrorBoundary はアプリ全体とウィンドウごとの 2 段、読み込み中は一覧を Skeleton・操作中を Spinner としてウィンドウごとに表示する — ユーザーの判断
- [決定] 会話はプロジェクトごとに切り替えられるようにする — ユーザーの判断
- [決定] プロジェクトごとに worktree を自由に作れるようにする — 並行で作業できるようにするため
- [決定] プロジェクトのファイルツリーとターミナルを初期版に入れる。rg でファイルの中身を検索し、Markdown やソースコードを開けるようにする — 検索して開く、コマンドを実行することがあるため
- [決定] タイムライン機能を入れ、skanehira/claude-timeline の動きをそのまま実現する — ユーザーの判断
- [決定] デザインは読むこと優先のエディターにする。本文は読みやすいゴシック体、コード・キー・ツリーは等幅とする。色は状態にだけ使い、選択は藤色、完了は緑、作業中は黄、自分待ちは桃色、差分は赤と緑とする。細い罫線で区切り、影と角丸は使わない — ユーザーの判断
- [決定] ダークとライトを用意し、OS の設定に合わせて切り替える — ユーザーの判断
- [棄却] 半透明の背景 — ユーザーが取り下げたため。ブラウザのページは後ろのデスクトップを透かせない
- [決定] `Ctrl+[` は、端末と同じく `Esc` と同じ働きをする。プロンプトも `Ctrl+[` で閉じられるようにする — ユーザーの判断
- [決定] ホームを含むすべてのウィンドウを、Vim のバッファと同じ使用感にする — ユーザーの判断

## 使い方の場面の聞き取り (2026-11-23)

- [聞き取り] 壁打ち: 長い回答は全体を読みながら、気になる点や質問をその都度書く
- [聞き取り] 壁打ち: 引用は、マウスで文章をコピーして `>` を付けて書いている
- [聞き取り] 壁打ち: AI の作業を待つ間は、他のプロジェクトの状況を確認し、必要ならプロンプトを打ち返す
- [聞き取り] 壁打ち: 前に何を決めたかは AI に経緯を聞くことが多く、コンテキストが無駄に増えてノイズになる
- [聞き取り] 壁打ち: 終わりには issue・ドキュメント・実装・調査などを AI にさせていることが多く、完了したらセッションを閉じる
- [決定] 会話で決まったこと・やめたこと・保留の一覧を持つ。AI が会話の区切りごとに候補を出し、利用者が直せる。元の会話のコンテキストは増やさない — 経緯を AI に聞くとコンテキストが増えてノイズになるため
- [決定] 会話を閉じるとき、できたものと残り (未コミットの変更、未送信のストックなど) を確かめられるようにする — ユーザーの判断
- [聞き取り] 並行: 終わりと返事待ちには、herdr のサイドバーの色とターミナル通知で気付いている
- [聞き取り] 並行: 2〜3 件を並行し、最大は 4〜5 件。見落として放置することはない
- [聞き取り] 並行: 別の会話を開いたら AI の回答の内容を精査して打ち返す。内容が複雑になると何の話か分からなくなり、会話を遡るか「今何の話をしているんだっけ」と会話を読まずに聞く
- [聞き取り] 並行: 打ち返す前に、今何をやっていて、どんな状況で、次に何を判断しないといけないかを考える。Claude Code の recap は 1〜2 行に凝縮されていて役に立たない
- [決定] 会話ごとに状況メモを持つ。根拠の発言へ飛べるようにし、会話のどこから読めばよいかも分かるようにする — 状況メモがあっても会話は読むが、状況を把握しやすくなるため
- [決定] 通知には、会話の題名と「次の判断」の 1 行目を書く — ユーザーの判断
- [決定] 文書はプレビューで読めるようにし、プレビューの上で Visual モードで選んで質問・指示・フィードバックができるようにする — ユーザーの判断
- [聞き取り] dev-spec: 文書は Neovim で Markdown をそのまま読むか、プレビューして読むことが多い
- [聞き取り] dev-spec: 直したい点は、Neovim の Visual モードで選び、`gl` でファイルパスをコピーし、`<leader>ac` でプロンプトを開いて貼り付けて伝えている
- [聞き取り] dev-spec: 面倒に感じる所や時間がかかる所は特に無い
- [聞き取り] 設計レビュー: ユースケースやユーザーストーリーなどの内容を確認し、問題なければ OK と返す。差し戻すときは普通に指摘を返す
- [保留] 状況メモの更新のしかた — skanehira/recap-plus を元に決める → 解決 (状況メモは「直近」と「目次」に分け、BR-012 で更新のしかたを決めた)
