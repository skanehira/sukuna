# 一覧と通知

- 種別: 機能設計書
- 対象 UC: UC-001 (docs/design/USECASES.md)

## 何を作るか

全プロジェクトの会話と issue を、開発者が次に対応する順に並べて見せ、対応が要る変化をブラウザの通知で知らせる。

**使う人**: 開発者 (1 人)。PC のブラウザから Vim のキーで使う。

**流れ**:

1. 一覧を開く。会話と issue が、判断待ち・指示待ち・作業中のセクションに分かれて並ぶ
2. 各行で、題名・状況・プロジェクト・最後の更新からの経過を読む。作業中の行には、今の工程・その経過・最後にしたことが出る
3. 行を選ぶと、その会話か issue が開く。作業中の行は、作業の末尾から開く
4. 左のツリーでプロジェクトを選ぶと、そのプロジェクトの issue が状態ごとに、会話が会話のセクションに並ぶ
5. その会話か issue を見ていないあいだに判断待ちか指示待ちに変わると、通知が届き、選ぶとその会話か issue が開く

**セクション**:

| セクション | 載るもの |
| --- | --- |
| 判断待ち | 設計の承認、AI の質問 (文章の質問を含む)、許可の確認、merge 前の確認、失敗・利用枠切れ・CI の失敗・依存先の取り下げで止まったもの、再起動で止まった会話 |
| 指示待ち | 質問なしで応答を終えた会話、開発者が止めた AI |
| 作業中 | AI が作業している会話と issue。応答をまとめている会話と、AI の開始を待つ issue を含む |

**主な決まり**:

- 状態は色ではなくセクションで分け、判断待ちをいちばん上に置く (BR-001)
- 下書き、依存先か実装の空きを待つ issue、完了と取り下げの issue、閉じた会話は載せない。issue のスレッドが判断を待つときは、その issue を載せる
- 同じセクションの中は、未読、優先度の高い issue、最後の更新が新しいものの順に並べる。会話は優先度が中の issue と同じ扱いにする (BR-074, BR-082)
- 開いたままでも、AI の状態が変わると行が動き、カーソルは同じ行について行く (BR-002, BR-083)
- 通知は、開発者が自分で止めた場合を除き、判断待ちか指示待ちに変わったときに 1 回だけ出す。どれかの端末で開いて見ている会話と issue には出さない (BR-003, BR-086)
- どれかの端末でその会話か issue を開くと、ほかの端末に残った通知も消える (BR-086)
- ページが安全なオリジンとして開かれていないときは、ブラウザの通知の代わりに、画面の中のお知らせとタブの題名の件数で知らせる。設定の画面に、通知を有効にする方法を出す

## 入出力と振る舞い

### この機能の前提

- 画面は UI_SKETCH.html の `pc-home` (一覧)、`pc-project` (プロジェクトの画面)、`pc-offline` (つながらないとき) を手本にする。どのウィンドウも Vim のバッファとして作る (DESIGN.md「画面の共通の作り」、作りは `features/buffer-ui.md`)
- 作業中の行の「工程・その工程の経過・最後にしたこと」の求め方は `features/work-monitor.md`「作業の状況の求め方」が正本である。本書はその結果を行に出す
- 未読かどうかは、会話の既読の位置 (`conversations.last_read_seq`) で決める。既読の位置を進める操作は `features/recap.md` が持つ
- 一覧・ツリー・プロジェクトの画面は、プロジェクトが解除されたもの (`projects.removed_at` がある) を含めない
- 一覧の組み立ては、DESIGN.md「データスキーマ」のインデックスを使う。担当の会話は `conversations (issue_id)`、スレッドは `conversations (parent_conversation_id)` で引く
- BR-005 (Vim のバッファと同じ操作感) は `features/buffer-ui.md` の土台で満たす。本書は一覧に固有のキーだけを書く

### 一覧のセクション分け

一覧に載せる単位は「行」である。行は、開発者が始めた会話 (`kind` が `chat`) 1 件か、issue 1 件のどちらかになる。精査・設計・実装の会話 (`kind` が `triage` / `design` / `impl`) は issue の行に畳み、スレッド (`kind` が `thread`) は元の会話の行に畳む。

issue の「担当の会話」は、issue のいまの段階を進める会話である。決め方は `features/issue.md`「担当の会話」の表に従う。

会話の行のセクション (閉じた会話 `closed_at` があるものは載せない):

| `run_state` | 条件 | セクション | 理由 |
| --- | --- | --- | --- |
| `working` | — | 作業中 | `working` |
| `waiting_answer` | — | 判断待ち | `question` |
| `waiting_permission` | — | 判断待ち | `permission` |
| `failed` | — | 判断待ち | `failed` |
| `usage_limited` | — | 判断待ち | `usage_limited` |
| `idle` | 番の終わりの待ちのあいだ (下の「番の終わりの待ち」) | 作業中 | `summarizing` |
| `idle` | 回答していない質問 (`questions.answered` が偽) が 1 件以上ある | 判断待ち | `question` |
| `idle` | 回答していない質問が無い | 指示待ち | `turn_ended` |
| `stopped` | `stop_reason` が `user` (開発者が止めた) | 指示待ち | `stopped_by_user` |
| `stopped` | `stop_reason` が `restarted` (ランナーの再起動で止まった) | 判断待ち | `restarted` |

- `stop_reason` の値は DESIGN.md「データスキーマ」のとおりで、`run_state` との対応は `features/conversation.md` の表に従う
- 再起動で止まった会話は判断待ちに置く。開発者が「再開する」か指示を送るまで動かないためである
- 待ちの消えた選択式の質問 (停止か再起動で AI が待たなくなった質問) は、回答以外の指示を届けて AI が次の応答を始めた時点で回答済みになる (`features/conversation.md`「選択式の質問と許可の確認」)。それまでは回答していない質問として数える

番の終わりの待ち: 番が終わって `idle` に移った会話は、その番が質問の一覧に反映されるか、反映に失敗するまで作業中に置く (BR-073)。

- 反映されたとは、`conversations.recap_seq` が `last_seq` 以上になったことを指す (`features/recap.md`)
- 失敗したとは、`recap_failed_at` が最後の `turn_end` のイベントの `created_at` 以降の時刻で立ったことを指す。失敗したときは、その時点の質問の一覧で判定する
- 通知の判定も、この待ちが済んでから行う。待たないと、指示待ちの通知のあとに質問が見つかり、判断待ちの通知がもう 1 回出る
- 待ちに時間の上限は置かない。更新の 1 回は `features/recap.md` が時間で打ち切るので、待ちは反映か失敗のどちらかで終わる
- ランナーの再起動で消えた更新は、ランナーが起動時に積み直す (`features/recap.md`「番ごとの更新」)

スレッドの扱い:

- 閉じていないスレッドのどれかが判断待ちの条件に当たるときは、元の会話の行を判断待ち (理由 `thread`) にする。元の会話そのものの判定より優先する
- 判断待ちの条件は、`run_state` が `waiting_answer` / `waiting_permission` / `failed` / `usage_limited` か、`stopped` (`restarted`) であることとする
- issue の担当の会話のスレッドが判断待ちの条件に当たるときも、issue の行を判断待ち (理由 `thread`) にする。issue の状態は問わない。下の issue の表で判断待ちになる行は、表の理由のままにする
- 会話を閉じると、そのスレッドの AI は止まる (BR-097)。閉じた会話の行は載せないので、そのスレッドも載らない
- 閉じた会話のスレッドに返信すると、元の会話が開き直される (`features/conversation-lifecycle.md`「開き直す (再開)」)。そのスレッドは、開き直した会話の行で扱う

issue の行のセクション:

| `issues.state` | 担当の会話の状態 | セクション | 理由 |
| --- | --- | --- | --- |
| 設計レビュー | 問わない | 判断待ち | `design_review` |
| 停止中 | 問わない | 判断待ち | 停止中の理由 (`issues.stop_reason` の値) |
| 精査待ち / 設計待ち / 実装中 | `waiting_permission` | 判断待ち | `permission` |
| 精査待ち / 設計待ち / 実装中 | `waiting_answer` / `failed` / `usage_limited` | 判断待ち | 会話の行と同じ |
| 精査待ち / 設計待ち / 実装中 | `stopped` (`user`) | 指示待ち | `stopped_by_user` |
| 精査待ち / 設計待ち / 実装中 | `working` | 作業中 | `working` |
| 精査待ち / 設計待ち / 実装中 | `idle` で、最後の番が開発者の発言で始まった | 指示待ち | `turn_ended` |
| 精査待ち / 設計待ち / 実装中 | 上記以外 (担当の会話がまだ無い、上に当たらない `idle`、`stopped` (`restarted`)) | 作業中 | `flow_waiting` |
| 下書き / 実装待ち / 完了 / 取り下げ | — | 載せない (上の「スレッドの扱い」に当たるときを除く) | — |

- `issues.state` の値の綴りと、停止中の理由 (`issues.stop_reason`) の値は `features/issue-flow.md` が正本である
- 段階の AI が選択式の質問で待つか、失敗か利用枠切れで止まると、`flow` が issue を停止中へ移す (`features/issue-flow.md`)。表の 4 行目は、移すまでのあいだの行である。許可の確認では停止中にしないので、3 行目で判断待ちに出す
- 開発者の発言で始まった番とは、`origin` が `developer`・`stock`・`queued`・`interrupt`・`answer_text` の `user_message` で始まった番である
- この番が報告なしで終わると、`flow` は催促も停止もしない (`features/issue-flow.md`「番の終わりで報告が無いとき」)。開発者の次の指示を待つので、指示待ちに置く
- この行も、会話の行と同じく番の終わりの待ちが済んでから判定する。待ちのあいだは作業中 (`summarizing`) に置く
- 担当の会話が `stopped` (`restarted`) の issue は、ランナーの再起動のあと `flow` が自動で続きを送る。開発者の対応は要らないので、作業中に置く
- 設計書を PR で入れる設定で承認した issue は、設計待ちに移り、設計の AI が PR を merge するあいだ作業中に出る (`features/design-review.md`)
- 理由が `flow_waiting` の行は、AI の開始を待つ issue である。状況の文は、自動フローが一時停止しているか、その段階が自動で処理する段階から外れているかで分ける (下の「状況の文」)
- 一時停止しているとは、全体 (`settings` の `flow_paused`) かプロジェクト (`projects.flow_paused`) のどちらかが一時停止のことを指す。段階が外れているとは、状態の段階 (精査待ちは `triage`、設計待ちは `design`、実装中は `impl`) が `projects.auto_stages` に無いことを指す (`features/project-settings.md`)

### 行の列

列は UI_SKETCH.html と同じく「題名 / 状況 / プロジェクト / 経過」の 4 つにし、ウィンドウの見出しに列の見出しを置く。

| 列 | 中身 |
| --- | --- |
| 題名 | issue は `#<番号> <題名>`、会話は `会話: <題名>` |
| 状況 | 下の「状況の文」 |
| プロジェクト | `projects.name` |
| 経過 | 最後の更新からの経過。下の「並びと経過」 |

状況の文:

| 理由 | 一覧の状況の文 | 通知の本文 |
| --- | --- | --- |
| `design_review` | 設計の承認 | 設計の承認を待っています |
| 停止中 (`merge_confirm`) | merge 前の確認 | merge 前の確認を待っています |
| 停止中 (`question`) | 質問: <detail> | <detail> |
| 停止中 (`failed`) | 失敗: <detail> | 失敗: <detail> |
| 停止中 (`usage_limit`) | 利用枠切れで停止 (<HH:MM> に再開) | 利用枠を使い切りました。<HH:MM> に自動で再開します |
| 停止中 (`ci_failed`) | CI の失敗: <detail> | CI が失敗しました: <detail> |
| 停止中 (`dependency_withdrawn`) | 依存先 <detail> の取り下げ | 依存先 <detail> が取り下げられました |
| `question` | 質問 <件数> 件: <1 件目の 1 行目> ほか | 1 件目の質問の 1 行目 |
| `permission` | 許可の確認: <ツール名> | 許可の確認: <ツール名>(<対象>) |
| `failed` | 失敗: <理由の 1 行目> | 失敗: <理由の 1 行目> |
| `usage_limited` | 利用枠切れで停止 (<HH:MM> に再開) | 利用枠を使い切りました。<HH:MM> に自動で再開します |
| `thread` | スレッド: <スレッドの理由の文> | スレッドの理由の通知の本文 |
| `turn_ended` | AI の最後の発言の 1 行目 | AI の最後の発言の 1 行目 |
| `stopped_by_user` | 止めました | (通知しない) |
| `restarted` | 再起動で止まりました | 再起動で作業が止まりました。再開するか指示を送ると続けます |
| `working` | <工程> <工程の経過> · <最後にしたこと> | (通知しない) |
| `flow_waiting` (一時停止している) | 自動フローを一時停止しています | (通知しない) |
| `flow_waiting` (段階が外れている) | 自動で処理しない段階です | (通知しない) |
| `flow_waiting` (そのほか) | 開始を待っています | (通知しない) |
| `summarizing` | 応答をまとめています | (通知しない) |

- 停止中の `<detail>` は、停止中へ移した最後の `state_changed` の `detail` である。中身は `features/issue-flow.md`「停止中の理由」に従う。`detail` が無いときは、`: <detail>` を付けずに書く
- 停止中 (`usage_limit`) の時刻は、担当の会話の `resets_at` から書く
- 利用枠の戻る時刻が無いときは、`(<HH:MM> に再開)` の代わりに `(15 分ごとに再開を試みる)` と書く (DESIGN.md「既知の制約」)
- `flow_waiting` の文は、一時停止しているかを先に見て、次に段階が外れているかを見る
- 状況の文は 1 行にし、列の幅を超える分は末尾を `…` で切る。通知の本文は 120 字で切る
- スレッドの回答があるときは、状況の文の前に `スレッドの回答 <件数> 件 · ` を付ける (下の「スレッドの回答の件数」)

### 並びと経過

- セクションの順は、判断待ち・指示待ち・作業中で固定する (BR-001)
- 同じセクションの中は、(1) 未読の行、(2) 優先度の高い順、(3) 最後の更新が新しい順に並べる (BR-074, BR-082)
- 優先度は issue の高・中・低で、値は `features/issue.md` が正本である。会話と、優先度の無い issue は中として扱う
- 3 つとも同じ行は、行の識別子 (ULID) の大きい順に並べ、並びを毎回同じにする
- 最後の更新の時刻は、会話の行ではその会話とスレッドの `last_activity_at` の最大、issue の行ではその issue のすべての会話の `last_activity_at` と最後の `issue_events.created_at` の最大とする (BR-084)
- 経過は、1 分未満を `<秒>秒前`、1 時間未満を `<分>分前`、1 日未満を `<時間>時間前`、それ以上を `<日>日前` と書く。画面が 30 秒ごとに計算し直す
- 並びの決まりは、サーバーと画面が同じ関数を使う (`src/shared/inbox/order.ts`)

### 未読の印

- 行は、次のどれかのとき未読とする。判断待ちか指示待ちの行に限り、作業中の行は未読にしない
  - 会話 (issue の行では担当の会話) に、`conversations.last_read_seq` より後の、開発者の発言 (`user_message`) 以外のイベントがある。決め方は `features/recap.md` の「未読の回答」と同じである
  - スレッドの回答の件数が 1 以上ある
- 担当の会話がまだ無い issue (例: 実装の前に依存先が取り下げられた issue) は未読にしない
- 未読の行は、行の左の印の桁に `●` を付け、題名を太字にする (UI_SKETCH.html の `listMarks`)
- 会話を開いて読むと、既読の位置が進み (`features/recap.md`)、配信で行の印が消える (BR-004)

### スレッドの回答の件数

- 元の会話のスレッドのうち、`run_state` が `idle` で、上の「未読の印」と同じく未読のイベントがあるものを数える (BR-085)
- 件数は、スレッドを開いて読むと減る。0 件になると状況の文の前置きも消える
- issue の行では、担当の会話のスレッドを数える

### 開いたままの更新とカーソルの追従

- 一覧を開くと、画面は配信の `inbox` を購読する。`changed` を受けたら `GET /api/inbox` で読み直す (配信の形は `features/runtime.md`「配信」)
- 読み直しは 1 秒に 1 回までにまとめる。1 秒のあいだに届いた `changed` は、最後に 1 回だけ読み直す
- 画面は、読み直した行で、バッファの行を書き換える。エディターの状態は作り直さない (BR-002、`features/buffer-ui.md`)
- カーソルのある行が動いたときは、カーソルを同じ行の識別子を持つ行へ移す (BR-083)
- カーソルのある行が一覧から消えたときは、カーソルを同じ行番号の行へ置く。行番号が最後の行を超えるときは最後の行へ置く
- 配信が途切れたあとにつながったときは、`GET /api/inbox` で読み直してから配信を受ける

### 一覧の操作

| 操作 | 画面に起きること |
| --- | --- |
| `Space h`、`:home`、`:ls` | 一覧を開く |
| `:project <名前>` | プロジェクトの名前を前方一致で引き、1 件に決まればそのプロジェクトの画面を開く。0 件なら「プロジェクトが見つかりません」、2 件以上なら「複数あります」をお知らせに出す |
| `j` / `k` / `/` / `n` など | Vim と同じに移動・検索する。セクションの見出しの行と説明の行にはカーソルを置けない (`features/buffer-ui.md`) |
| 判断待ちか指示待ちの行で `Enter` | 会話の行は会話を、issue の行は issue を開く。未読があれば未読の先頭から表示する (`features/recap.md`) |
| 作業中の行で `Enter` | その会話を開く。開いた時点で AI が作業中 (`run_state` が `working`) なら、カーソルを最後の行に置く (`features/recap.md`)。issue の行は、issue の会話の表示を同じ規則で開く |

- issue を開いたときに最初に出す表示 (会話・設計・差分) は、issue の状態で決まる。決まりは `features/issue.md` に従う
- 判断待ちの行が 1 件も無いときは、判断待ちのセクションに「判断待ちはありません」の行を出し、ほかのセクションはそのまま出す。指示待ちと作業中も、行が無ければ「指示待ちはありません」「作業中はありません」を出す
- セクションの見出しの行には、セクション名と行の件数を出す
- ステータス行の右に、判断待ち・指示待ち・作業中の件数を出す (UI_SKETCH.html の `pc-home`)

### 左のツリー

ツリーは、ほかのウィンドウと同じく読み取り専用の Vim のバッファにする。中身は次の順に並べる。

1. `一覧` の行
2. プロジェクトごとに、プロジェクト名の見出しの行。自動フローを一時停止しているプロジェクトは、名前の後に `(自動フロー停止中)` を付ける
3. その下に、閉じていない会話 (`会話: <題名>`) を始めた順に、完了と取り下げ以外の issue (`#<番号> <題名>`) を番号の小さい順に並べる
4. `アプリ` の見出しの下に `設定` と `ヘルプ` の行

- プロジェクトは登録した順に並べる
- いま主のウィンドウで開いている会話・issue・プロジェクト・画面の行に、印の桁の `›` を付ける
- 行で `Enter` を押すと、その画面を開く。プロジェクト名の見出しの行は、プロジェクトの画面を開く
- 画面は配信の `inbox` を購読し、`changed` を受けたら `GET /api/projects` で読み直して行を書き換える。カーソルは同じ行について行く

### プロジェクトの画面

プロジェクトの画面は、issue を状態ごとのセクションに、会話を会話のセクションに分けて並べる (BR-101)。手本は UI_SKETCH.html の `pc-project` である。

- セクションの順は、停止中、設計レビュー、実装中、設計待ち、精査待ち、実装待ち、下書き、完了、取り下げ、会話とする。issue が 0 件の状態のセクションは出さない
- 見出しの行には、状態の名前と件数を出す
- 列は「題名 / 状況 / 経過」の 3 つにする。状況は、一覧に載る状態なら一覧と同じ文にする
- 実装待ちの状況は、次の順に見て、最初に当たる文にする。順は `features/implementation-flow.md`「始める順と件数」の条件の順である

| 当たるもの | 状況の文 |
| --- | --- |
| 子がある (親の issue) | `子の完了を待つ` |
| 完了していない依存先がある | `#<番号> の完了を待つ` (番号のいちばん小さい依存先) |
| 親が設計待ち・設計レビュー・停止中 (停止前の状態が設計待ち) のどれか | `親 #<番号> の設計を待つ` |
| 自動フローが一時停止している | `自動フローを一時停止しています` |
| 実装が自動で処理する段階から外れている | `自動で処理しない段階です` |
| そのほか | `実装の空きを待つ` |

- 完了と取り下げの issue は、残した worktree があれば `worktree を残しました: <パス>` にする。無ければ `—` にする
- 残した worktree とは、`issue_events` の `worktree_kept` が指す worktree のうち、`worktrees.removed_at` が空のものを指す (`features/implementation-flow.md`「worktree の片付け」)
- 下書きは `—` にする
- 完了と取り下げ以外のセクションは、優先度の高い順、同じなら番号の小さい順に並べる。完了と取り下げは、閉じた時刻 (`issues.closed_at`) の新しい順に並べる
- 完了と取り下げは、それぞれ新しい順に 10 件を出し、残りは `ほか <件数> 件を表示する` の 1 行に畳む。その行で `Enter` を押すと、残りを読み込んで展開する。展開したかどうかはブラウザのタブごとに覚える
- 会話のセクションは、閉じていない会話を最後の更新が新しい順に並べる。状況は、一覧に載っていれば一覧と同じ文、載っていなければ `—` にする
- issue の行で `Enter` を押すと issue を、下書きの行は issue の作成・編集の画面を開く。issue の行の `cc` は、その issue の編集の画面を開く。`dd` は取り下げの確認を出す。どれも中身は `features/issue.md` が持つ
- issue も会話も無いときは「issue はまだありません。Space o で作ります。」と出す
- 画面は配信の `inbox` を購読し、`changed` の `project_ids` にこのプロジェクトがあれば、`GET /api/projects/:id/overview` で読み直す

### サーバーにつながらないとき

- 最後に取得した一覧・ツリー・プロジェクトの画面を、画面のメモリーに残したまま表示する。ステータス行の表示はアプリシェルの決まりに従う (DESIGN.md「アプリシェル」)
- つながらないあいだも、経過は時計で計算し直す
- つながると、`GET /api/inbox` (プロジェクトの画面なら `GET /api/projects/:id/overview`) と `GET /api/projects` を読み直し、表示を入れ替える。開発者の操作は要らない (UC-001 E1)
- ページを再読み込みしたときに残す仕組みは持たない。安全なオリジンではない構成では Service Worker を使えないためである

### 通知

#### 通知を有効にする条件

決定: ブラウザの通知は Web Push と Service Worker で作り、ページが安全なオリジンとして開かれているときだけ有効にする。
理由: `http://macstudio:<port>` では Chrome が Service Worker と通知を使わせない。Chrome の例外指定か HTTPS で開いたときは使える (FEASIBILITY.md「PoC 結果」web-push-tailscale)。
採らなかった案: Tailscale の HTTPS で配信する (`tailscale serve` を使わない決定のため)。

- 画面は、起動時に `window.isSecureContext` と `navigator.serviceWorker` の有無を見る。両方そろうときだけ Service Worker (`/sw.js`、範囲は `/`) を登録する
- 通知の許可は、設定の画面で開発者が「通知を有効にする」を選んだときだけ求める。許可されたら購読を作り、`POST /api/push/subscriptions` で登録する
- 購読に使う VAPID の公開鍵は `GET /api/settings` の応答から取る (`features/operations.md`)
- 通知が使えない端末と、許可されていない端末では、下の「画面の中のお知らせ」で知らせる

#### 通知を出す条件

- 行が判断待ちか指示待ちのセクションに入ったときに、その行について 1 回だけ出す (BR-003)。作業中から入ったときと、一覧に無かった行が入ったときが当たる
- 指示待ちから判断待ちへ移ったときも出す。判断待ちから指示待ちへ移ったときは出さない。同じセクションのまま理由だけが変わったときも出さない
- 理由が `stopped_by_user` のときは出さない。開発者が自分で止めたためである
- 解除したプロジェクトを登録し直して一覧に戻った行には、出さない。新しい変化ではなく、外していた行が戻っただけだからである
- 会話の行は、未読のときだけ出す。記録が 0 件の会話 (最初の指示なしで始めた会話) が指示待ちに入っても、本文の無い通知を出さないためである
- 番の終わりの通知は、「番の終わりの待ち」が済んで、行が判断待ちか指示待ちに入ったときに出す。番の終わりの待ちのあいだ、行は作業中にあるためである
- 再起動で止まった会話 (理由 `restarted`) は判断待ちに入るので、会話ごとに 1 回出す
- 出す前に、どれかの端末がその対象を見ているかを調べ、見ていれば出さない (BR-086)。判定は下の「見ている」を使う
- 出したか、見ているので出さなかったかは、`notifications` に 1 行で記録する。見ていて出さなかったときは、`dismissed_at` を作った時刻と同じにする
- 1 回だけの判定は、行がそのセクションに入った時刻より後に作った `notifications` の行が、同じ対象にあるかで行う。あれば出さない
- 行がセクションに入った時刻は、上の規則で通知の対象になる移り変わりのときだけ書き換える。判断待ちから指示待ちへ移ったときと、理由だけが変わったときは書き換えない
- この時刻は、サーバーが行ごとにメモリーに持つ。サーバーの起動時は、会話の `last_activity_at` か最後の `issue_events.created_at` で代える。サーバーが止まっていたあいだの変化も、起動後に 1 回だけ通知する

スレッドの通知:

- スレッドは、元の会話とは別の通知の対象にする (BR-085)。対象の種類は会話で、識別子はスレッドの識別子である
- 次のどちらかのときに、スレッドの通知を 1 回出す (P4)
  - スレッドが `idle` に移り、そのスレッドの「番の終わりの待ち」が済んだとき
  - スレッドが判断待ちの条件 (上の「スレッドの扱い」) に当たったとき。選択式の質問、許可の確認、失敗、利用枠切れ、再起動で止まったときである
- 1 回だけの判定は、この時刻を入った時刻として行う
- 本文は、スレッドを会話の行と同じに判定した理由の「通知の本文」とする
- 元の会話か issue の行が、理由 `thread` で判断待ちに入ったことでは、別の通知を出さない

worktree を残したこと:

- 通知にしない。対応が要る変化ではなく、プロジェクトの画面の完了か取り下げの行と、issue の画面で分かるためである (`features/issue.md`)
- ランナーは `worktree_kept` を記録して知らせるだけで、一覧は `inbox` の `changed` で読み直す
- Web Push を送るのは画面のサーバーだけで、ランナーから通知を出す道は作らない

「見ている」の判定:

- 見ている対象は、`features/runtime.md`「いま見ているもの」の決め方に従う
- ページが見えている接続が、主のウィンドウか右のウィンドウに出している対象として送った会話・スレッド・issue が当たる
- ファイルの表示のためだけの購読は、見ていることに含めない
- スレッドは、スレッドか元の会話のどちらかを見ていれば、見ているとする
- どれか 1 台の端末で見ていれば、ほかの端末にも出さない

#### 通知の文面

| 項目 | 中身 |
| --- | --- |
| 題名 | issue は `#<番号> <題名> (<プロジェクト名>)`、会話は `<題名> (<プロジェクト名>)`、スレッドは `スレッド: <スレッドの題名> (<プロジェクト名>)` |
| 本文 | 「状況の文」の表の「通知の本文」。判断することか応答の 1 行目 |
| tag | `<対象の種類>:<対象の識別子>` (例: `issue:01J…`)。スレッドは `conversation:<スレッドの識別子>` とする。同じ対象の新しい通知は前の通知を置き換える |
| 開く先 | 会話は `/conversations/<識別子>`、issue は `/issues/<識別子>`、スレッドは `/conversations/<元の会話の識別子>?thread=<スレッドの識別子>` |

push の中身は `{ "type": "show", "tag": "…", "title": "…", "body": "…", "url": "…" }` とする。送る期限 (TTL) は 24 時間にする。

#### 通知を選んだとき

- Service Worker は、通知を閉じてから、アプリのウィンドウを探す。あれば前面に出し、`{ "type": "navigate", "url": "…" }` を送って一覧を経ずにその画面へ移らせる。無ければ `clients.openWindow(url)` で開く (UC-001 A)
- 画面の URL と、URL から画面を開く決まりは `features/buffer-ui.md` に従う
- 開いた画面は、ふだんの開き方と同じに未読の先頭から表示する

#### ほかの端末の通知を消す

- 次のどれかが起きたら、その対象の通知を取り下げる (BR-086)
  - どれかの端末で、その対象を見ている状態になった (上の「見ている」の判定)
  - 行が判断待ちと指示待ちのどちらでもなくなった
  - 会話を閉じた。その会話とスレッドの通知を取り下げる (`features/conversation-lifecycle.md`)
  - 会話を削除した。その会話とスレッドの通知を取り下げる (`features/conversation-lifecycle.md`「削除」)
  - プロジェクトを解除した。そのプロジェクトの会話と issue の通知を取り下げる (`features/project-settings.md`)
- 取り下げは、`notifications.dismissed_at` を書き、全部の購読へ `{ "type": "dismiss", "tag": "…" }` の push を送る。Service Worker は同じ tag の通知を探して閉じる
- 会話を閉じる処理、会話の削除、プロジェクトの解除は、画面のサーバーの中で本書の取り下げの口 (`notify.ts`) を、対象を渡して呼ぶ。削除では、`notifications` の行を消すトランザクションより前に呼ぶ
- `dismissed_at` がすでにある通知には、取り下げの push を送らない

#### 画面の中のお知らせとタブの題名

- サーバーは、通知を出すたびに、配信の `app` の `notice` を全部の接続へ送る。`message` は `<題名>: <本文>` にし、`notification: { "tag", "url" }` を足す (`features/runtime.md` の `notice` に足す項目)
- この端末で通知が有効でないとき、画面はこれを「お知らせ」として出す。ほかのお知らせと同じく 4 秒で消す (DESIGN.md「アプリシェル」)
- 通知が有効な端末では、`notification` の付いた `notice` を出さない。OS の通知と二重になるためである
- タブの題名は、未読の判断待ちと指示待ちの行の件数を前に付けて `(<件数>) sukuna` にする。0 件のときは `sukuna` にする。通知が有効かどうかに関係なく付ける

#### 設定の画面の通知の節

設定の画面 (`:set`) の作りは `features/operations.md` が持つ。本書は「通知」の節の中身を決める。

| 端末の状態 | 出す行 |
| --- | --- |
| 安全なオリジンではない | `通知  使えません (このページは安全なオリジンとして開かれていません)` と、有効にする方法の説明 |
| 使えるが購読していない | `通知  この端末では止まっています` と、メニューの行「通知を有効にする」 |
| 購読している | `通知  この端末で有効` と、メニューの行「この端末の通知を止める」 |
| 許可が拒否されている | `通知  ブラウザで拒否されています` と、サイトの設定から許可し直す説明 |

有効にする方法の説明は、次の 2 つを並べる。どちらを使うかは開発者が決める (DESIGN.md「未解決の論点」)。

- Chrome で `chrome://flags/#unsafely-treat-insecure-origin-as-secure` を開き、このアプリのオリジン (例: `http://macstudio:<port>`。ポートまで一致させる) を登録して、Chrome を再起動する
- サーバーに証明書を持たせ、HTTPS で開く

「この端末の通知を止める」は、購読を解除し、`DELETE /api/push/subscriptions/:id` を呼ぶ。購読の識別子は、登録の応答で受けてブラウザの `localStorage` に持つ。

## API

共通の規約 (本人の判定、エラーの形) は DESIGN.md「横断規約」の「本人の判定」と「エラー応答」に従う。

### GET /api/inbox

一覧の全部の行を、セクションごとに並べて返す。

```json
{
  "sections": [
    { "name": "decision", "rows": [ /* 行 */ ] },
    { "name": "instruction", "rows": [] },
    { "name": "working", "rows": [] }
  ]
}
```

`name` は `decision` (判断待ち)・`instruction` (指示待ち)・`working` (作業中) の 3 つで、この順に返す。行の形は次のとおりである。

```json
{
  "key": "issue:01JD…",
  "kind": "issue",
  "id": "01JD…",
  "project": { "id": "01JC…", "name": "shop-api" },
  "title": "#42 在庫の引き当てを追加する",
  "section": "decision",
  "reason": "design_review",
  "status": "設計の承認",
  "notice": "設計の承認を待っています",
  "unread": true,
  "priority": "high",
  "lastActivityAt": 1764140000000,
  "threadAnswers": 0,
  "activity": null,
  "issue": { "number": 42, "state": "<issues.state の値>", "stopReason": null }
}
```

- `key` は `issue:<識別子>` か `conversation:<識別子>` で、カーソルの追従に使う
- `reason` は「一覧のセクション分け」の表の理由の値である。停止中の issue では `issues.stop_reason` の値を入れる
- `status` は一覧の状況の文、`notice` は通知の本文である。理由が `working` の行の `status` は空にし、画面が `activity` と時計から作る
- `activity` は理由が `working` の行だけに入り、形は `features/work-monitor.md`「API」の `activity` と同じである
- `issue` は issue の行だけに入る。会話の行では `null` にする
- `priority` は、会話と優先度の無い issue では `null` にする

### GET /api/projects

左のツリーに出すプロジェクトと、その会話と issue を返す。

```json
{
  "projects": [
    {
      "id": "01JC…",
      "name": "shop-api",
      "flowPaused": false,
      "conversations": [ { "id": "01JE…", "title": "予約 API の壁打ち" } ],
      "issues": [ { "id": "01JD…", "number": 42, "title": "在庫の引き当てを追加する", "state": "<issues.state の値>" } ]
    }
  ]
}
```

- `conversations` は、閉じていない `chat` の会話だけを、始めた順に返す
- `issues` は、完了と取り下げ以外を、番号の小さい順に返す

### GET /api/projects/:id/overview

プロジェクトの画面の中身を返す。

| クエリ | 意味 |
| --- | --- |
| `closed` | `all` を付けると、完了と取り下げを全件返す。付けないと、それぞれ新しい順に 10 件まで返す |

```json
{
  "project": { "id": "01JC…", "name": "shop-api", "flowPaused": false },
  "issueSections": [
    { "state": "<issues.state の値>", "total": 23, "rows": [ { "key": "issue:01JD…", "id": "01JD…", "number": 9, "title": "通知メールの文面", "status": "—", "lastActivityAt": 1764050000000, "unread": false } ] }
  ],
  "conversations": [ { "key": "conversation:01JE…", "id": "01JE…", "title": "予約 API の壁打ち", "status": "質問 2 件: 期限切れの戻し方 ほか", "lastActivityAt": 1764139700000, "unread": true } ]
}
```

- `total` はその状態の issue の件数で、`rows` の件数より多ければ、画面は残りを畳んだ行を出す
- 失敗: プロジェクトが無いか解除済みなら 404 `not_found`

### POST /api/push/subscriptions

この端末の Web Push の購読を登録する。

```json
{ "endpoint": "https://fcm.googleapis.com/fcm/send/…", "keys": { "p256dh": "…", "auth": "…" }, "userAgent": "Mozilla/5.0 …" }
```

- 応答: 新しく登録したら 201、同じ `endpoint` がすでにあれば 200 で、どちらも `{ "id": "01JF…" }` を返す
- 失敗: `endpoint` が `https://` で始まらないか、`keys` が欠けていれば 400 `invalid_input`

### DELETE /api/push/subscriptions/:id

この端末の購読を消す。応答は 204 とする。無い識別子は 404 `not_found` を返す。

### 配信の topic

topic の一覧と形は `features/runtime.md`「配信」が正本である。本書が使うのは次の 2 つである。

| topic | `type` | 本書での使い方 |
| --- | --- | --- |
| `inbox` | `changed` | 一覧・ツリー・プロジェクトの画面が API で読み直す |
| `app` | `notice` | `notification` (`{ "tag", "url" }`) の付いたものを、通知が有効でない端末でお知らせとして出す |

## エッジケースの決定

1. 空・最小データ: プロジェクトが 1 つも無いときは、一覧に「プロジェクトがありません。:set からプロジェクトを登録します。」を出す。セクションに行が無いときは「<セクション名>はありません」を出す (UC-001 D)。題名が空の会話は `会話: (題名なし)` と出す
2. 上限・境界値: 状況の文は 1 行で、列の幅を超える分を `…` で切る。通知の本文は 120 字で切る。経過は 59 秒まで `<秒>秒前`、60 秒ちょうどから `1分前`、60 分ちょうどから `1時間前`、24 時間ちょうどから `1日前` にする。プロジェクトの画面の完了と取り下げは、10 件目まで出し 11 件目から畳む。一覧の行数に上限は設けない
3. エラー時に利用者へ見えるもの: 一覧の取得に失敗したら、主のウィンドウにエラーと「再読み込み」を出す (DESIGN.md「アプリシェル」)。購読の登録に失敗したら、お知らせに `message` を出し、設定の画面は「止まっています」のまま残す。push の送信先が 404 か 410 を返したら、その購読を消す。それ以外の送信の失敗はログに残し、やり直さない。一覧とタブの題名で知らせが残るためである
4. 並行操作・二重実行: 変化が続いたときは、画面の読み直しを 1 秒に 1 回にまとめる。購読の登録を 2 回送っても、同じ `endpoint` は 1 件にまとめる (200 を返す)。通知を出す判定は行ごとに 1 つずつ順に行い、同じ対象に 2 回出さない
5. 再表示時の整合: 一覧・ツリー・プロジェクトの画面は、開くたびと配信がつながり直すたびに API で読み直す。配信だけで画面の状態を作らない (DESIGN.md「配信」)。別の画面から一覧へ戻ったときも読み直し、カーソルは前に置いていた行の識別子へ戻す
6. 表示の寿命: 未読の印は、既読の位置が AI の最後の出力に追いつくと消える。スレッドの回答の件数は、そのスレッドを読むと減る。画面の中のお知らせは 4 秒で消える。OS の通知は、対象を見たときか、行が判断待ちと指示待ちから外れたときに消える。オフラインの表示は、つながったときに消える
7. 送る前のデータ: 該当なし (一覧と通知には、開発者が書いて送る内容が無い)。プロジェクトの画面の畳みを展開したかは、ブラウザのタブごとに `sessionStorage` に持つ (P3)
8. 状態の移り変わり: 行のセクションは「一覧のセクション分け」の 2 つの表だけで決まる。開発者が止めた issue の AI は指示待ちに移り、指示を送ると作業中に戻る。再起動で止まった会話は判断待ちに移り、再開か指示で作業中に戻る。設計レビューの issue に発言を送ると、設計待ちになり作業中へ移る (`features/design-review.md`)。一時停止を解くと、`flow_waiting` の issue は AI が始まって `working` に移る
9. 自動で進むこと: 行の計算し直しと配信、通知の送信と取り下げ、つながり直したあとの読み直しは、開発者の操作なしに行う。番の終わりの通知は、質問の一覧の更新が済むか失敗するまで待ってから出す。送信に失敗した通知はやり直さない
10. 端末と画面をまたぐこと: 未読と既読、通知の送信と取り下げの記録は、サーバーに持ち、端末の間で共有する (P3)。カーソルの位置と、プロジェクトの画面の展開はタブごとに持つ。どれか 1 台で見ている対象には、どの端末にも通知を出さない。通知の購読は端末 (ブラウザ) ごとに持つ
11. 並びと数え方: セクションの中は、未読、優先度、最後の更新、識別子の順に並べる。経過は、その会話か issue で AI か開発者が最後に何かをした時刻から数える (BR-084)。セクションの見出しとステータス行の件数は、そのセクションの行数を数える。タブの題名の件数は、未読の判断待ちと指示待ちの行を数える

- 判断待ちの判定の 3 行は、セクションの判定の関数を表の全行で回す単体テストで確かめる
- 通知の 5 行の結合テストは、Web Push の Port を偽物に差し替え、本物の SQLite で行の変化を起こす。番の終わりの待ちは、`recap_seq` と `recap_failed_at` を書いて済ませる
- 「通知を選ぶと開く」は、Service Worker の処理を、偽物の `clients` で単体テストにする。ヘッドレスのブラウザでは OS の通知を選べないためである
- 「一覧を開いたまま行が移る」は、配信の `changed` を受けて `GET /api/inbox` を読み直し、行が新しいセクションへ移るまでを結合テストで確かめる。画面を通す流れは `features/issue-flow.md` の E2E が、一覧を開いたままなぞる
- 「判断待ちの行を選ぶと開く」と「作業中の行を選ぶと末尾から開く」は、画面の単体テストで、開く画面とカーソルの行を確かめる。キーで開く流れは E2E の 1 本が通る

E2E 対象動線: （US-024）一覧の上で、Vim と同じ移動・検索・選択のキーを使い、行を選んで会話を開くまでをキーボードだけで行える
