# 作業の見張りとタイムライン

- 種別: 機能設計書
- 対象 UC: UC-011 (docs/design/USECASES.md)

## 何を作るか

AI が動いている会話と issue について、AI が考え中かツールを実行中か、今の工程・その経過・最後にしたことと、AI が立てた計画の進み具合を見せる。AI を止められ、続きの依頼と相談を会話の AI に届ける。

**使う人**: 開発者 (1 人)。作業に時間がかかっていると感じたときや、どこまで進んだか知りたいときに使う。

**流れ**:

1. 一覧の作業中の行を選ぶと、その会話が作業の末尾から開く。ウィンドウの下端に、形の変わり続ける印と「考え中」か「ツールを実行中」が出て、経過が 1 秒ごとに進む。issue では今の工程とその経過も出て、AI がツールを使った後は最後にしたことも出る
2. タイムラインを開くと、AI が立てた計画が、重みの付いたタスクの木と進捗の割合で右に出る
3. タスクを選ぶと、説明・メモ・重み・完了した単位・変更の履歴が出る
4. そのまま続けさせるか、止めるか、タスクについて相談するか、木の続きを頼むかを選ぶ
5. 止めた作業は保存され、指示を送ると続きから動く

**主な決まり**:

- 工程は、精査・設計・実装・レビュー・PR・CI 待ち・merge のどこにいるかを示す。開発者が始めた会話の工程は「応答」とする (BR-055)
- タイムラインは、AI の計画を記録するプラグイン (claude-timeline) が会話ごとに保存するファイルを読んで出す。ファイルは書き換えない
- 進捗の数え方と表示は、そのプラグインと同じにする。割合は小数 2 桁で出し、残りがあるあいだは 100% にしない (BR-053, BR-054)
- 定期レポートは、AI が 3 分以上の間隔で書いた短い報告を新しい順に並べる
- 相談と続きの依頼は、会話へのふつうの指示として届く。AI が作業中なら、今の作業が終わってから届く
- 止めると、AI と裏で動くコマンドが止まり、会話は指示待ちになる。指示を送ると続きから動く (BR-056)
- エージェントの出力を並べる表示と、issue の情報の表示は作らない

## 入出力と振る舞い

### この機能の前提

- 画面は UI_SKETCH.html の `pc-issue-working` (作業中の会話)、`pc-issue-working--timeline` (タイムライン)、`pc-issue-working--task` (タスクの詳細) を手本にする
- 会話の表示、指示の送信、停止、届く前の指示の扱いは `features/conversation.md` が持つ。本書はそれらの API を呼ぶ
- issue の「担当の会話」の決め方は `features/issue.md`「担当の会話」に従う
- タイムラインは DESIGN.md「データスキーマ」のとおり、アプリのデータベースに写さない
- 本書は「作業の状況の求め方」の正本である。`features/inbox.md` の作業中の行も、ここで求めた値を出す

### 作業の状況の求め方

作業の状況は「工程」「工程の経過」「最後にしたこと」の 3 つで表す。会話か issue の AI が `working` のときだけ求める。

工程と、その始まりの時刻:

| 対象 | 工程 | 工程の始まり |
| --- | --- | --- |
| 開発者が始めた会話とスレッド | 応答 | 今の番を始めた開発者の発言 (再開を含む) のイベントの `created_at` |
| 精査待ちの issue | 精査 | 精査待ちに移った `issue_events` の `created_at` |
| 設計待ちの issue | 設計 | 設計待ちに移った `issue_events` の `created_at` |
| 実装中の issue | 最後の段階の記録 (下の表)。記録が無ければ実装 | 実装中に移った時刻と、最後の段階の記録の時刻の新しいほう |

実装中の段階は、`issue_events` の種類 `stage_changed` (`{ "stage": "<段階>" }`) で読む。種類の一覧は `features/issue-flow.md`「`issue_events` の種類」、記録するときは `features/implementation-flow.md`「実装の段階の記録」が正本である。

| `payload.stage` | 画面の工程 |
| --- | --- |
| `implement` | 実装 |
| `review` | レビュー |
| `pr` | PR |
| `ci` | CI 待ち |
| `merge` | merge |

- 工程の経過は、工程の始まりから今までの時間とする。1 分未満を `1分未満`、1 時間未満を `<分>分`、それ以上を `<時間>時間<分>分` と書く。一覧の行では 30 秒ごとに、作業中の表示では 1 秒ごとに計算し直す
- 最後にしたことは、今の番で最後に届いたツールの実行 (`tool_use`) を `<ツール名>(<対象>)` と書く。issue では担当の会話を見る

| ツール | 対象に書くもの |
| --- | --- |
| `Bash` | コマンドの 1 行目 |
| `Read` / `Edit` / `Write` / `NotebookEdit` | ファイルのパス (会話の作業ディレクトリからの相対) |
| `Grep` / `Glob` | 探した語 (`pattern`) |
| `WebFetch` | URL |
| `Task` / `Agent` | 頼んだ作業の説明 (`description`) |
| MCP のツール (`mcp__<サーバー>__<ツール>`) | 名前を `<ツール>` だけにし、対象は書かない |
| そのほか | 対象は書かない |

- 最後にしたことは 60 字で切り、超える分を `…` にする
- 今の番にツールの実行がまだ無いときは、`応答を作成中` と書く
- 求め方の関数は `src/shared/activity/` に置き、サーバーと画面が同じものを使う。画面は、配信で届いたイベントから最後にしたことを更新する

### 作業中の会話の表示

- 開いた時点で AI が作業中 (`run_state` が `working`) の会話は、カーソルを最後の行に置いて開く (`features/recap.md`)。カーソルが最後の行にあるあいだだけ、新しい出力について行く (BR-093、`features/conversation.md`)
- issue の行から開いたときは、issue の会話の表示で、担当の会話を同じく末尾から開く
- AI が `working` のあいだ、会話に作業中の表示を出す。置き場所は `features/conversation.md` が持つ。文は次の形にし、`[ ]` の部分は条件を満たすときだけ出す (UI_SKETCH.html の `pc-issue-working`・`pc-issue-working--thinking`・`pc-conv--working`)

```text
<印> <動き>… <番の経過>[ / <工程> <工程の経過>][ / 最後にしたこと: <最後にしたこと>]
```

| 部分 | 中身 |
| --- | --- |
| 印 | 形の変わり続ける 1 文字 (下の「印の動き」) |
| 動き | 今の番で、サブエージェントでないツールの実行 (`parent_tool_use_id` が空の `tool_use`) のうち、同じ `tool_use_id` の `tool_result` がまだ届いていないものがあれば `ツールを実行中`。無ければ `考え中`。サブエージェントを動かすツール (`Task`・`Agent`) も親のツールの実行なので、サブエージェントが動いているあいだは `ツールを実行中` になる。このとき最後にしたことには、サブエージェントが使ったツールが出る |
| 番の経過 | 起点から今までの時間。起点は、今の番の始まり (最後にしたことと同じく、最後の `user_message` か `resumed` のイベント) と、その後に開発者が質問か許可の確認に答えたイベント (`answer`・`permission_decision`) のうち、新しいものの `created_at` とする。1 分未満を `<秒>秒`、1 時間未満を `<分>分<秒>秒`、それ以上を `<時間>時間<分>分` と書く。今の時刻が起点より前 (端末の時計のずれ) なら `0秒` とする |
| 工程・工程の経過 | 「作業の状況の求め方」の値。工程が `応答` のときは出さない。指示を送ってからの時間で、番の経過とほぼ重なるためである |
| 最後にしたこと | 「作業の状況の求め方」の値。今の番にツールの実行がまだ無いときは出さない。`応答を作成中` は一覧の行にだけ出す |

例:

- 開発者が始めた会話で、指示を送った直後: `✻ 考え中… 8秒` (UI_SKETCH.html の `pc-conv--working`)
- 実装中の issue で、テストを流しているとき: `✻ ツールを実行中… 2分5秒 / 実装 11分 / 最後にしたこと: Bash(npm test -- csv)`
- 同じ issue で、テストの結果が届いた後: `✻ 考え中… 2分31秒 / 実装 11分 / 最後にしたこと: Bash(npm test -- csv)`

印の動き:

- 印は `·` から始め、`·` `✢` `✳` `✶` `✻` `✽` `✻` `✶` `✳` `✢` の 10 コマを繰り返す。`✽` まで進んだら、同じ形を逆にたどって `·` に戻る。1 コマを 120 ミリ秒ずつ出す
- 印は 1 文字分の幅に固定する。形が変わっても、後ろの文字は動かない
- 次のあいだは印を `✻` で止める。番の経過は止めずに進める
  - OS で動きを減らす設定 (`prefers-reduced-motion: reduce`) にしているとき
  - 画面がサーバーとつながらないとき (DESIGN.md「アプリシェル」のつながらないことの表示が出ているあいだ)。このあいだは AI の様子が画面に届かない。印を動かし続けると、作業が続いていると誤って伝えてしまう
- 番の経過は 1 秒ごとに計算し直す。毎回、時計の今の時刻と番の始まりの差から求め、1 秒ずつ足していかない。タブが裏に回ってタイマーが遅れても、戻ったときに正しい値になる
- 印と経過を書き換えるのは、作業中の表示の部品だけにする。会話のバッファは描き直さない。キーの操作への応答の基準 (BR-072) を、作業中も守るためである
- 作業中の表示の文、動き、番の経過は、画面だけが求める。一覧の行と進捗の API の `activity` は変えない

- 工程・工程の経過・最後にしたことは、会話を開いたときに進捗の API の `activity` で読み、その後は配信で届いたイベントで更新する。動きと番の始まりは、画面が会話のイベントから求める

決定: 動きは「考え中」と「ツールを実行中」の 2 つにする
理由: テストやビルドを流しているあいだも「考え中」と出すと、AI が考えているのか、長いコマンドを待っているのかを見分けられない
採らなかった案: Claude Code のように、番ごとに違う動詞を出す (AI が何をしているかを表さない)

決定: 作業中の表示に、AI が出力したトークンの数を出さない
理由: 画面に届くトークンの数は、番の終わりの `turn_end` の `usage` だけである。番の途中の数を出すには、ランナーから新しい知らせを配信する必要がある (`features/runtime.md`「Agent SDK のメッセージからの写し方」)。動く印と 1 秒ごとに進む経過で、作業が続いていることは分かる
採らなかった案: Claude Code と同じく、番の途中のトークンの数を出す (ランナーの写し方と配信の形を変えることになる)

### タイムラインの読み方

決定: タイムラインは、プラグインが保存するファイルをサーバーが読み、木と進捗を組み立てて画面へ返す。
理由: Agent SDK の会話でもプラグインが動き、会話ごとのファイルに木が保存される (FEASIBILITY.md「PoC 結果」agent-sdk-conversation)。
採らなかった案: 会話のイベントの `timeline_tasks` の呼び出しから組む (定期レポートと相談の記録がファイルにしか無いため)。

- ファイルの場所は `<設定のディレクトリ>/timeline/sessions/<session_id>.json` とする。設定のディレクトリは、環境変数 `CLAUDE_CONFIG_DIR` があればその値、無ければ `~/.claude` である。`session_id` は `conversations.session_id` を使う
- 画面のサーバーとランナーは同じ環境変数で起動する (`features/operations.md`)。両方が同じファイルを指す
- ファイルの形は `{ version: 1, journal: [{ at, toolUseId, agentId?, ops: [...] }], reports: [{ at, text }], comments: [{ at, taskId, text }] }` である。`comments` が無いファイルは空の配列として読む
- `version` が 1 でないか、`journal` と `reports` が配列でないファイルは、読めないファイルとして扱う
- 木は、`journal` の `ops` を古い順に当てて組み立てる。当て方と、受け付けない操作の扱いは、プラグインの `hooks/tree.ts` と同じにする

`ops` の当て方:

| 操作 | 当て方 | 受け付けないとき |
| --- | --- | --- |
| `add` | タスクを足す。重みの既定は 1、状態の既定は未着手 | 同じ id がある、親が無い |
| `update` | 書かれた項目だけを変える | id が無い。子を持つタスクへの状態と完了した単位は無視し、ほかの項目は当てる |
| `remove` | そのタスクと子孫を消す | id が無い |
| 共通 | — | 重みが 0 以下、完了した単位が `[完了, 全体]` で 0 ≤ 完了 ≤ 全体、全体 > 0 を満たさない、未着手なのに完了した単位が 1 以上 |

受け付けない操作は、その操作だけを飛ばし、同じ呼び出しのほかの操作は当てる。

### 進捗の数え方

- 親の無いタスク 1 つが、1 本の木である。木の題名は、その親の無いタスクの題名とする
- 子の無いタスクは、完了なら 1、そうでなければ完了した単位の割合 (完了 ÷ 全体。単位が無ければ 0) を、完了した分として数える
- 状態を書かずに完了した単位を書いたタスクは、単位から状態を決める。0 なら未着手、途中なら進行中、全部なら完了とする
- 完了にしたタスクは、完了した単位を全体に揃える
- 子のあるタスクは、子の割合を子の重みで按分して足す。重みは同じ親の下のタスクどうしで比べる
- 子のあるタスクの状態は子から決める。全部が完了なら完了、進行中があれば進行中、停止があって進行中が無ければ停止、完了と未着手が混ざれば進行中、それ以外は未着手とする
- 残りのある木とタスクは、99.99% を上限にする。100% は、その下のタスクがすべて完了のときだけ出す
- 割合は、100 倍して小数 2 桁に丸めて `50.00%` と書く (BR-054)

例: 重み 3 の完了と、重み 1 の未着手が並ぶと 75.00%。重み 1 で単位が `[1, 2]` のタスクが、重み 1 と 3 の完了と並ぶと 90.00% で、そのタスクの行は 50.00% になる。

### タイムラインの表示

`Space t` で、右のウィンドウに「タイムライン」を開く。会話か issue を開いていないときは「会話か issue を開くと、タイムラインを使えます。」と出す。

- 出す木は、ブラウザのタブごとに選んだ木を覚え、その木があるあいだは保つ。選んでいなければ、進行中のタスクを含む木、無ければいちばん新しく足した木を出す
- `]t` と `[t` で、次と前の木へ移る

右のウィンドウの行は、次の順に並べる。

| 行 | 中身 |
| --- | --- |
| 木 | `<位置> / <木の数>  <木の題名>` |
| 状態 | 木の状態 (未着手・進行中・完了・停止) |
| 進み | `<割合>  (末端のタスク <完了の数> / <末端の数>)` |
| 内訳 | 末端のタスクの状態ごとの数。0 の状態は書かない (例: `完了 2 · 停止 1 · 未着手 1`) |
| 経過 | 木を足してからの時間。足した時刻が分からなければ `—` |
| 帯 | 完了・進行中・停止・未着手の割合を、緑・黄・赤・灰の帯で示す |
| タスク | 列の見出し「タスク / 状態 / 進み」の下に、木の中のタスクを深さ優先で並べる。深さごとに 4 字下げ、行の先頭に状態の印 (`○` 未着手、`◐` 進行中、`●` 完了、`✕` 停止) を付ける |
| 報告 | 見出し `報告 (3 分ごと)` の下に、定期レポートを新しい順に並べる。1 件は時刻の行と本文の行で、時刻は今日なら `HH:MM`、それ以外は `MM/DD HH:MM` |
| 操作 | メニューの行「続きを依頼する」 |

- 計画がまだ無いとき (ファイルが無いか、木が 1 本も無いとき) は、タスクの行の代わりに「タスクの木はまだありません。AI が計画を立てると、ここに出ます。」を出す。定期レポートがあれば、その下に出す。メニューの行は出さない
- 定期レポートが無いときは、報告の見出しの下に「報告はまだありません」を出す
- ファイルが読めないときは、前に読めた中身を出し、上に「タイムラインのファイルを読めませんでした。前に読めた内容を出しています。」を出す。前に読めた中身が無ければ、その文だけを出す

### タスクの詳細

タスクの行で `Enter` を押すと、右のウィンドウを「タスクの詳細」に替える。`Ctrl+h` でタイムラインへ戻る。

| 行 | 中身 |
| --- | --- |
| タスク | 題名 |
| 状態 | 未着手・進行中・完了・停止 |
| 木 | 木の題名 |
| 進み | そのタスクの割合 |
| 重み | 重み |
| 完了した単位 | 子の無いタスクは `<完了> / <全体>` (単位が無ければ未完了は `0 / 1`、完了は `1 / 1`)。子のあるタスクは、完了した末端のタスクの数と末端の数 |
| 説明 | `description` |
| メモ | `note` |
| コメント | 見出しの下に、このタスクへの相談を古い順に `<時刻>  あなた: <文>` で並べる。無ければ「コメントはありません」 |
| 履歴 | 見出しの下に、このタスクの変更を新しい順に並べる |
| 操作 | メニューの行「このタスクについて相談する」 |

- 履歴の 1 行は `<YYYY/MM/DD HH:MM:SS>  <変更の後の状態>  <前の割合> → <後の割合>  重み <重み>` とし、その変更で書いた説明とメモ、サブエージェントの id があれば後ろに足す。時刻が分からなければ日時を `—` にする
- 子のあるタスクには、子の変更で状態か割合が動いたときにも履歴を 1 行足す。最新の履歴の状態は、タスクの状態と一致する
- コメントは、ファイルの `comments` のうちこのタスクのものと、この会話で開発者が送った相談を合わせて作る。同じタスク・時刻・文の組は 1 つにまとめる。相談の読み方は「相談コメントの保存と抽出」に従う

### 続きを依頼する

- タイムラインのメニューの行「続きを依頼する」を選ぶと、次の文を、その会話への指示として送る (`POST /api/conversations/:id/messages`、`features/conversation.md`)

```text
タイムラインのタスクツリー「<木の題名>」の作業を続けてください。
```

- 文はプラグインの日本語の文面と同じにする (BR-053)。確認を挟まず、`preserveDraft: true` で送る。書きかけの入力は残る
- AI が作業中なら、指示は届く前の指示として預かられ、今の作業が終わってから届く。届く前なら取り消せる (BR-009)
- 送ったら、お知らせに `続きを依頼しました` か `続きの依頼を預けました` を出す

### 相談

- タスクの詳細のメニューの行「このタスクについて相談する」を選ぶと、会話の入力欄を開き、次の前置きを入れて Insert モードにする

```text
タイムラインのタスク <タスクの id>「<タスクの題名>」について: 
```

- 書きかけの入力が空なら、前置きを先頭に入れる。空でなければ、末尾に空行を足してから前置きを入れる。書きかけはふだんの入力欄と同じくサーバーに残る (P1、`features/conversation.md`)
- 送り方、届く前の指示の扱いは、ふだんの指示と同じである。AI には、どのタスクの話かが前置きで伝わる
- 前置きの文面は、「続きを依頼する」と同じくプラグインに合わせる。アプリはファイルの `comments` に書かない

### 相談コメントの保存と抽出

相談は、表示する文とは別にタスクの ID と本文を保存し、それを読取りの正本にする。
決定: 送信の `timeline_comments` に、`[{ "task_id": "<ID>", "text": "<本文>" }]` を渡す。
理由: ID と題名に引用符や改行があると、表示する文だけでは所属や本文の始まりを一意に戻せない。
採らなかった案: 最長の前置きから所属と本文を推測する。

画面は、開発者が選んだタスクの ID と、入力欄の前置き・本文の範囲を `timeline_anchors` に記録する。
各要素は `task_id`、前置きの最初の位置 `from`、本文の最初の位置 `bodyFrom`、本文の終わりの位置 `to` を持つ。
位置は文の先頭からの UTF-16 コード単位で、`to` の位置の文字を含まない。範囲は文の順に並べ、互いに重ねない。
前置きの中を編集すると、同じ文字を貼り直した場合も、その相談先の指定を外す。本文の中を編集すると、同じタスクの相談として文の範囲を更新する。
端末をまたいでも相談を続けられるよう、下書きと預かった指示には文と範囲を一緒に保存する。
預かった指示の編集で範囲を指定したら、相談の本文も更新する。取り消した指示を下書きに戻すときは、追記した位置に範囲を移す。取り消しを戻すときは、その指示だけを再送し、別の書きかけを残す。

位置を持たない旧形式の相談は、保存済みの ID と本文を使う。文頭の前置きに続く 1 件の本文を特定できるときは、編集できる範囲に戻す。
本文の位置を特定できないときは、元の文の範囲 `from` と `to`、原文 `originalText`、保存済みの ID と本文 `comments` を同じ `timeline_anchors` に残す。
その範囲の原文が変わっていたら、入力欄に相談先を選び直す案内を出す。元の文に戻せば、保存済みの組のまま送れる。

入力欄は、保存した範囲とタスクの ID から送信の `timeline_comments` を作る。表示する `text` は「相談」の前置きを保つ。
画面のサーバーは、指示の送信 API で受けた配列を、ランナーの `POST /conversations/:id/messages` の同名の項目に渡す。
`timeline_comments` と `timeline_anchors` は省略できる。相談の配列には ID と本文を文字列で入れ、改行・引用符・空白・空文字列を保つ。
配列以外の値や、文字列でない ID・本文は 400 `invalid_input` にする。
相談画面は、この送信の接続点を使って相談の配列を渡す。

- 作業中に預けるときは、`queued_instructions.timeline_comments` の JSON に配列を保存する。`NULL` は構造化情報の無い入力、`[]` は相談を含まないことを明示した入力である
- 直接送るときも、預かった指示をまとめて送るときも、配列を入力の順に連結して `user_message.payload.timeline_comments` に残す。本文は切り詰めず、末尾の改行も保つ
- 構造化情報のある入力と無い入力をまとめるときは、情報の無かった入力の原文だけを `user_message.payload.timeline_legacy_texts` の配列に残す。構造化情報のある部分は前置きから読み直さない
- すべての入力に構造化情報が無いときは、上の 2 項目を省略し、既存の発言と同じく `payload.text` から読む。配列を明示した入力は、空配列でもこの読取りに戻さない
- 配達と割り込みでも情報を保つ。キューの削除と発言の保存は同じトランザクションで行い、失敗したらキューを残す。二重送信は `client_id` の初回の結果を返し、相談を足し直さない
- 相談として取り込むのは、開発者由来の `developer`・`queued`・`interrupt`・`stock`・`answer_text` の発言だけとする。`flow`・`resume`・`finish_proposal` は取り込まない

構造化情報の無い発言は、現在と履歴の ID・題名から作った前置きが行頭にあるかを調べる。
同じ ID と同じ前置きの候補は 1 つとして扱う。別々の相談は、次の前置きの直前の改行 1 つか空行 1 つで区切る。
所属と本文の始まりが一意なら、複数タスクの相談もそれぞれに付ける。判定が曖昧な原文は分割せず、どのタスクにも付けない。
`timeline.unresolvedComments` に `{ "at": <発言の時刻>, "text": "<原文全体>", "reason": "<理由>" }` として古い順に返す。
混在した配達では、構造化情報の無かった各入力を 1 つの原文として扱い、時刻には配達した発言の時刻を使う。

| 理由 | 条件 |
| --- | --- |
| `ambiguous_task` | 同じ位置から同じ本文の始まりを指す前置きに、別の ID が対応する |
| `ambiguous_boundary` | 別の長さの前置きが同じ位置に合う、または ID・題名の改行の中に別の候補の前置きがある |

複数の曖昧さがある原文は `ambiguous_boundary` を優先する。同じ時刻・原文・理由の組は 1 つにまとめる。
プラグインのファイルは読み取りだけに使い、構造化情報や未確定の原文は書き込まない。

### 止める

- 会話か issue を開いているとき、`Space x` か `:stop` で AI を止める。タイムラインかタスクの詳細にカーソルがあっても効く
- 止める処理は `POST /api/conversations/:id/stop` (`features/conversation.md`) を呼ぶ。issue では担当の会話を止める。AI と、裏へ移ったコマンドが止まり、会話の記録は保存される (DESIGN.md「既知の制約」)
- 止めた会話は `run_state` が `stopped`、`stop_reason` が `user` になり、一覧では指示待ち (理由 `stopped_by_user`) に移る。届く前の指示は届けずに残す (BR-088)
- 確認は挟まない。止めた作業は、指示を送れば続きから動くためである (BR-056)
- 止められたら、お知らせに「<送り先> の AI を止めました。作業は保存され、指示待ちになります」を出す (文の決まりは `features/conversation.md`)。止める AI が無ければ 409 が返り、その `message` (「止める AI がありません」) をお知らせに出す (`features/conversation.md`)
- 止めた issue の状態は変えない。自動フローは、開発者が止めた担当の会話を、指示が送られるまで動かさない (`features/issue-flow.md`)
- 止めたあとに指示を送ると、同じ会話を再開して続きから動く (`features/conversation.md`)

### タイムラインの更新

- タイムラインかタスクの詳細を開いているあいだ、画面はその会話の配信 `conversation:<会話の識別子>` を購読する
- その購読があるあいだ、サーバーはその会話のタイムラインのファイルを見張る
- ファイルの変更、`timeline_tasks` の実行の保存、開発者の相談の配達を、最初の変更から 300 ミリ秒ごとにまとめて配信する。配信は `changed` で、`parts` に `timeline` を入れる
- 預けた相談は、会話に配達されるまでタスクのコメントには出さない
- 画面は `parts` に `timeline` がある `changed` を受けると、進捗の API を読み直して表示を入れ替える。カーソルは同じタスクの行について行く
- 購読がなくなったら、見張りを止める
- issue の担当の会話が替わったときは (例: 精査から設計へ)、画面は新しい担当の会話のタイムラインを読み直す

## API

共通の規約 (接続範囲、エラーの形) は DESIGN.md「横断規約」の「接続範囲」と「エラー応答」に従う。

### GET /api/issues/:id/progress

issue の担当の会話について、作業の状況とタイムラインを返す。

```json
{
  "conversationId": "01JE…",
  "activity": {
    "stage": "implement",
    "stageLabel": "実装",
    "stageStartedAt": 1764139000000,
    "lastAction": "Bash(npm test -- csv)",
    "lastActionAt": 1764139600000
  },
  "timeline": {
    "defaultTreeId": "t1",
    "trees": [
      {
        "id": "t1",
        "title": "注文 CSV の文字化けを直す",
        "status": "in_progress",
        "completed": 0.5,
        "parts": { "completed": 0.5, "in_progress": 0.25, "blocked": 0.25, "pending": 0 },
        "leaves": { "total": 4, "completed": 2, "in_progress": 0, "blocked": 1, "pending": 1 },
        "startedAt": 1764138500000
      }
    ],
    "tasks": [
      { "id": "t2", "parent": "t1", "title": "CSV の書き出し", "status": "in_progress", "weight": 3, "description": "…", "note": "…", "done": [1, 2], "completed": 0.5, "units": "1 / 2" }
    ],
    "history": [
      { "at": 1764139320000, "taskId": "t2", "title": "CSV の書き出し", "from": "pending", "to": "in_progress", "weight": 3, "completedBefore": 0, "completedAfter": 0.5, "description": null, "note": "正常系が完了", "agentId": null }
    ],
    "reports": [ { "at": 1764139320000, "text": "文字コードの判定が終わり、書き出しの正常系を実装した。" } ],
    "comments": [ { "at": 1764139200000, "taskId": "t2", "text": "BOM 付きのときの扱いも決めてください" } ],
    "unresolvedComments": []
  },
  "readError": null
}
```

- `activity` は、担当の会話が `working` でないときは `null` にする。`stage` の値は `review`・`pr`・`ci`・`merge`・`implement`・`triage`・`design`・`reply` のどれかである
- `timeline` は、担当の会話が無いとき、`session_id` がまだ無いとき、ファイルが無いときは `null` にする。ファイルがあって木が 0 本のときは `trees` を空にして返す
- `trees` は足した順、`tasks` は木ごとに深さ優先の順に返す
- `history` と `reports` は新しい順、`comments` と `unresolvedComments` は古い順に返す
- `status` の値は、プラグインと同じ `pending`・`in_progress`・`completed`・`blocked` である
- `readError` は、ファイルが読めないときに理由の文を入れる。そのとき `timeline` は前に読めた中身か `null` にする
- 失敗: issue が無ければ 404 `not_found`

### GET /api/conversations/:id/progress

開発者が始めた会話とスレッドについて、`GET /api/issues/:id/progress` と同じ形で返す。`conversationId` はその会話、`activity.stage` は `reply` (応答) になる。会話が無ければ 404 `not_found` を返す。

### 配信

配信の topic と形は `features/runtime.md`「配信」が正本である。本書は `conversation:<会話の識別子>` の `changed` の `parts` に `timeline` を足して使う。

| topic | `type` | 本書での使い方 |
| --- | --- | --- |
| `conversation:<会話の識別子>` | `changed` (`parts` に `timeline`) | 画面が進捗の API を読み直す |
| `conversation:<会話の識別子>` | `event` | 画面が最後にしたことを更新する |

## エッジケースの決定

1. 空・最小データ: ファイルが無いか木が 0 本なら「タスクの木はまだありません。AI が計画を立てると、ここに出ます。」を出す (UC-011 E1)。説明・メモが無いタスクは、その行に `—` を出す。今の番にツールの実行が無ければ、一覧の行では最後にしたことを `応答を作成中` にし、作業中の表示では最後にしたことを出さない。番の始まりのイベントがまだ読めていないときは、作業中の表示に番の経過を出さず、`✻ 考え中…` のように印と動きだけを出す
2. 上限・境界値: ファイルは 4 MiB まで読む。超えるときは読めないファイルとして扱う (プラグインが 1 回に書ける上限と同じ)。割合は 99.99% を上限にし、残りが無いときだけ 100.00% を出す。最後にしたことは 60 字で切る。工程の経過は 59 秒まで `1分未満`、60 分ちょうどから `1時間0分` と書く。番の経過は 59 秒まで `59秒`、60 秒ちょうどから `1分0秒`、60 分ちょうどから `1時間0分` と書く。起点より前の時刻では `0秒` と書く
3. エラー時に利用者へ見えるもの: ファイルが読めないときは、前に読めた中身と「タイムラインのファイルを読めませんでした。前に読めた内容を出しています。」を出す。続きの依頼と相談の送信、止める操作が失敗したら、応答の `message` をお知らせに出し、入力欄の文は残す (`features/conversation.md`)
4. 並行操作・二重実行: プラグインが書いている途中に読んで形が壊れていたら、200 ミリ秒後に 1 回だけ読み直す。それでも読めなければ、前に読めた中身を返す。続きの依頼を続けて 2 回選ぶと、2 通の指示になる。AI が作業中なら、届く前の指示として 2 件並び、取り消せる。止める操作を止まったあとにもう一度送ると、409 を受け、`message` をお知らせに出す (`features/conversation.md`)
5. 再表示時の整合: タイムラインは開くたびと、`parts` に `timeline` がある `changed` を受けるたびに、進捗の API で読み直す。配信がつながり直したときも読み直す。作業中の表示の工程と最後にしたことは、会話を開くたびに API の `activity` で読み直し、その後は配信のイベントで更新する
6. 表示の寿命: 作業中の表示は、AI が `working` でなくなると消え、印と経過を書き換えるタイマーも止める (`features/conversation.md`)。読めないファイルの案内は、次に読めたときに消える。お知らせは 4 秒で消える (DESIGN.md「アプリシェル」)
7. 送る前のデータ: 相談の文は会話の書きかけの入力として、サーバーに残す (P1)。続きの依頼は文を書かないので、送る前のデータが無い。選んでいる木はブラウザのタブごとに `sessionStorage` に持つ (P3)
8. 状態の移り変わり: 止めると会話は `stopped` になり、一覧の指示待ちへ移る。指示を送ると `working` に戻り、作業中へ移る。issue の状態は止めても変わらない。担当の会話が替わると、タイムラインは新しい会話のものに替わる
9. 自動で進むこと: ファイルの見張りと読み直し、配信、作業中の表示の印の動きと経過の計算し直しは、開発者の操作なしに行う。続きの依頼と相談は、開発者が選んだときだけ送る (P2)。止めた会話は、自動フローでも指示が送られるまで動かさない
10. 端末と画面をまたぐこと: タイムラインの中身はファイルが正本で、どの端末でも同じになる。相談の書きかけは、会話の書きかけとして端末の間で共有する。開いている木、タイムラインを開いているか、カーソルの位置はタブごとに持つ (P3)
11. 並びと数え方: タスクは木ごとに深さ優先、定期レポートは新しい順、履歴は新しい順、コメントは古い順に並べる。末端のタスクは子の無いタスクを数える。工程の経過は工程の始まりから、番の経過は今の番の始まりか、その後に質問や許可の確認に答えた時刻の新しいほうから、木の経過は木を足した時刻から数える。質問や許可の確認に答えると、答えた時刻から数え直すので、答える前の時間は番の経過に入らない

- 進捗の数え方の単体テストは、上の「進捗の数え方」の例 (75.00%、90.00% と 50.00%、99.99% の上限) と、受け付けない操作の各行を入れる
- 工程の単体テストは、工程の表の各行と、段階の記録の有無、最後にしたことのツールの表の各行を入れる。時計は Port で差し替え、作業中の表示のタイマーは偽のタイマーで進める。番の経過の書き方は、DESIGN.md「開発・検証コマンド」の property テストでも確かめる (正の性質の例: 1 時間未満の秒数 n から書いた文を分と秒に読み戻すと n になる)
- 結合テストは、`CLAUDE_CONFIG_DIR` を一時ディレクトリにし、そこにタイムラインのファイルを置いて読ませる。Agent SDK は Port の偽物にし、届いた指示の文を完全一致で確かめる
- 相談の単体・API 結合テストは、次の条件表を両方で固定する。5 種類の開発者由来の取り込みと、ほかの 3 種類の除外も確かめる

| 条件 | 構造化情報あり | 構造化情報なし |
| --- | --- | --- |
